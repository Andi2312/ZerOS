# Архитектура ZerOS Mobile

## Суть

ZerOS Mobile — **своя оболочка на базе Android** по модели One UI / HyperOS: Android остаётся
ядром и фреймворком (AMS, WMS, SurfaceFlinger, PackageManager), а весь видимый слой — наш.

Это значит:

- **SystemUI не отключаем, а заменяем своим**: статус-бар, шторка, быстрые настройки,
  локскрин, недавние, панель громкости, меню питания — наш код и наше оформление.
- **Свой домашний экран** (ZerOS Home) вместо штатного лаунчера.
- **Свои приложения**: звонилка, SMS, камера, галерея, файлы, настройки, часы.
- **Своё оформление**: шрифт, звуки, иконки, bootanimation, название и версия в «О телефоне».
- **Android-приложения работают штатно** — Play и любые APK ставятся как обычно.
- **`.zpk` — дополнительный формат** для наших приложений, не замена APK.

Целевое устройство — **Galaxy A5 2016 (a5xelte)**: LineageOS 17.1 (Android 10, API 29),
разблокированный загрузчик, TWRP и Magisk. Root здесь не «опция», а рабочий инструмент:
без него нельзя заменить SystemUI и системные приложения.

## Android — ядро, лицо — наше

Мы не «режем» Android и не выключаем его интерфейс. Мы работаем как производители прошивок:
ядро и фреймворк остаются, а всё, что видит пользователь, заменяется нашим.

| Не делаем | Делаем вместо этого |
|---|---|
| отключение `com.android.systemui` | **свой SystemUI**: сначала RRO-тема, затем форк из исходников |
| выпиливание системных сервисов | используем AMS/WMS/SurfaceFlinger как есть |
| свой оконный менеджер и свой рендер | Android View, стандартные окна и `Surface` |
| отказ от APK | любые APK ставятся и запускаются штатно |
| патчи ядра | root через Magisk, где нужен привилегированный вызов |

Штатный лаунчер и системные приложения остаются в системе как резерв: если наша замена
сломается, всегда можно вернуться к ним. Любой шаг обратим (Magisk-модуль отключается).

### Root на A5

На A5 root есть (Magisk), и он нужен для:

- замены SystemUI и системных приложений в `/system/priv-app`;
- тихой установки APK и управления задачами;
- прямого доступа к `/data/media/0`;
- своих звуков, шрифтов и bootanimation (Magisk-модуль);
- смены `ro.build.*` для «О телефоне» (`resetprop`).

На устройстве без root часть вещей тоже работает (ZerOS Home, `.zpk`, обычные приложения),
но полного вида «своя ОС» там не будет: SystemUI останется андроидным.

### Root на эмуляторе (стенд)

Для отладки системных сценариев (установка в `/system`, замена системных приложений,
правка `/data`) Magisk не нужен: образ AVD — `userdebug`, в нём уже есть `su`,
а `adb root` включает root прямо в `adbd`.

Порядок:

```powershell
shell\avd.ps1            # Pixel_4 с -writable-system, затем adb root + adb remount
shell\install-system.ps1 # APK в /system/priv-app + reboot
```

Отличия от телефона:

- `/system` нельзя перемонтировать в `rw` без `-writable-system` при старте AVD;
  с флагом система монтируется overlayfs поверх `super` и реально пишется;
- правки `/system` живут в образе AVD, пока не сделан `-wipe-data`;
- проверка целостности (dm-verity) на userdebug не мешает, на A5 её надо
  учитывать при прошивке.

Стенд нужен, чтобы обкатать замену SystemUI и системных приложений до того,
как трогать A5.

## Процессы ZerOS

| Компонент | Роль | Реализация |
|---------|------|-----------|
| **ZerOS SystemUI** | статус-бар, шторка, быстрые настройки, локскрин, recents, громкость, меню питания | наш SystemUI в `priv-app`; в первой версии — RRO-тема штатного, дальше форк |
| **ZerOS Home** (`zerosh`) | рабочий стол, меню приложений, поиск, хост `.zpk` | обычный APK с intent-фильтром HOME |
| `.zpk`-приложение | пакет ZerOS | **не регистрируется в PackageManager/AMS**: его жизненный цикл ведёт Home/`zhoster` |
| `zpkd` | установка/удаление/проверка/реестр `.zpk` | Java + наши парсеры, внутри процесса Home |
| `zhoster` | запуск пакетов, песочница, права | Java + рантайм-хосты |
| `zpy` | Python-рантайм (CPython + JNI) | C + JNI — **не в v0.1** |
| `zweb` | Web-рантайм (WebView-обёртка + мост API) | Java — единственный рантайм в v0.1 |

Android-приложения запускаются штатно через `Intent` — Home для них обычный лаунчер.
Через границу процесса — **Binder** и **файловые сокеты** для рантаймов.

## Графика

Телефонный Shell — **обычные Android View** (`RecyclerView`, `TextView`, `ImageView`,
`ViewPager2`). Это даёт бесплатно клавиатуру, IME, автозамену, выделение текста,
доступность, масштабирование и поворот экрана. Свой GL-рендер для оболочки не нужен:
на K7 (1 ГБ, Mali-400) он только добавит работы.

`.zpk`-приложения в v0.1 рисуются внутри `WebView` — браузерный движок уже оптимизирован
под слабое железо лучше, чем самодельный рендер. Если позже понадобится свой рендер для
игр/канваса, он добавляется как отдельный рантайм (`zeros.canvas.*`), а не как основа Shell.

## IPC/API: как приложения говорят с системой

`.zpk`-приложение (web/py) получает объект `ZerOS` с методами (см. `docs/zeros-api.md`).
Под капотом — мост в Shell, но приложение об этом не знает:

```
// web
ZerOS.notify({ title: 'Привет', text: 'мир' })
ZerOS.fs.write('/user/docs/a.txt', 'данные')
// python
from zeros import api
api.notify('Привет', 'мир')
```

## Разделение по этапам

1. **ZerOS Home** — свой рабочий стол и меню приложений на LineageOS, штатный SystemUI пока на месте.
2. **Оформление** — RRO-тема: цвета, иконки, шрифт, звуки, bootanimation, «О телефоне».
3. **Свои приложения** — часы, калькулятор, файлы, галерея, затем звонилка и SMS.
4. **Свой SystemUI** — сначала рестайл штатного, потом форк: шторка, быстрые настройки,
   уведомления, recents, локскрин, громкость.
5. **`.zpk`** — `zpkd`, web-рантайм, порты с часов и DOOM.
6. **Своя сборка** — LineageOS 17.1 с нашими пакетами, своими ключами и брендингом.
7. **Свои системные приложения** — настройки, камера, замена остальных штатных.

## Приложения: рантаймы и портирование

`.zpk` — наш формат для собственных и портированных приложений. Android-приложения при этом
никуда не деваются: их можно запускать как обычные APK. То есть ZerOS UI — это и лаунчер для
Android-приложений, и хост для `.zpk`.

- **Рантайм `web`** (v0.1) — база для всех портов: приложения пишутся на HTML/JS и говорят с системой
  через мост ZerOS API.
- **Рантайм `python`** — CPython + JNI: тянет готовые сетевые библиотеки (например, Telethon для MTProto)
  и тяжёлую логику.
- **Рантайм `jvm`** — Android и так исполняет DEX, поэтому «порт Java/Kotlin» — это не порт, а загрузчик:
  `InMemoryDexClassLoader` в отдельном процессе + наш API. Зато сразу открываются готовые библиотеки
  (TDLib JNI, OkHttp, Ktor).
- **Android-приложения (APK)** — запускаются штатно через `Intent`; Shell показывает их в меню
  наравне с `.zpk`. Ничего пересобирать не нужно.
- **Порты с часов**: переписываются с Zepp API на ZerOS API вручную и пакуются в `.zpk`.
- **Свои системные приложения** (звонилка, SMS, галерея, файлы, камера) — после Shell.

### Что нужно от сервисов Shell для «сетевых» портов

Telegram, MAX и подобные — это не статичные страницы, а постоянные соединения. Если держать их внутри
WebView, то при сворачивании приложения соединение умрёт и пуш не придёт.

- **Протокол живёт в сервисе, а не в UI.** Правильный путь для мессенджеров — нативный клиент в
  foreground-сервисе Shell (TDLib — C++ с JNI), а UI подписывается на события. Это касается не только
  мессенджеров, но и любой фоновой сети.

- **Фоновые соединения живут в сервисе**, а не в WebView: WebSocket/MTProto-сессия, реконнект, хранение
  сессии — на стороне сервиса.
- **Уведомления** показываем через системный `NotificationManager` (работает без root) и дублируем
  в собственный список Shell; для перехвата чужих уведомлений — `NotificationListenerService`.
- **WebView подключается к уже живой сессии** и просто рисует интерфейс.
- Отсюда же глубокие ссылки, бейджи, счётчики непрочитанного.

Порядок включения: ZerOS Home → оформление (RRO) → свои приложения → свой SystemUI → `.zpk` → своя сборка.
До последнего шага система остаётся штатной LineageOS, и всё можно откатить.

### Python и GUI

Python не тащит с собой тулкит. Он работает **headless-воркером**: сеть, разбор, хранение, состояние,
TDLib. Интерфейс описывается декларативным деревом, Shell рендерит его нативно.

- Почему не Kivy/pygame: свой GL-рендер означает свою реализацию ввода, IME, автозамены, выделения
  текста, буфера обмена, масштаба и поворота. На Android это самая дорогая часть — и она уже есть в Shell.
- Нативный рендер даёт нормальную клавиатуру, автозамену, выделение и доступность бесплатно.
- Для нестандартных экранов остаётся immediate-mode API (`zeros.canvas.*`): Python шлёт команды
  рисования, Shell исполняет.
- Обмен — JSON по сокету: `ui.patch`, `ui.event`, `net.request`, `notify`.
- Одно дерево UI используется и web-, и python-приложениями, поэтому порт с web на python не меняет вид.

TDLib из Python вызывается через `ctypes` и JSON-интерфейс `libtdjson.so`
(`td_json_client_create/send/receive/execute`), JNI не нужен; приём событий — в отдельном потоке,
наружу — в `asyncio`.

## Эмулятор — первая целевая платформа

Android как база нужен, чтобы ZerOS Shell был обычным APK и работал на любом телефоне без перепрошивки.
А для разработки нужен **эмулятор на ПК**: не надо каждый раз брать в руки устройство, чтобы проверить
экран или пакет. В эмуляторе при этом можно крутить «железо»: заряд, внешнюю освещённость, геопозицию,
картинку с камеры, акселерометр и т.п.

Что это меняет в архитектуре:

- **Shell не знает про железо.** Всё идёт через `zhal` (ZerOS HAL) — единый интерфейс к питанию,
  датчикам, камере, гео, времени.
- **На эмуляторе `zhal` — локальный сервис на хосте** (или вообще in-process в Shell): панель «крутилок»
  говорит со Shell **напрямую**, без `adb emu` и без Android-костылей. Просто выставляет значения
  в `zhal` — заряд, свет, гео, поворот, картинку камеры.
- **`zdb` — полный аналог adb для нас**: установка пакетов, логи, shell, файлы, скриншоты и плюс
  `zdb hal …` — инъекция «железа» (в эмуляторе пишет в `zhal`, на устройстве читает реальные датчики).
- **На устройстве тот же `zhal`** — над реальными Android-сенсорами и сервисами. Код Shell один.
- **Профиль эмулятора под K7**: 480×854, 1 ГБ RAM, API 22, x86 — чтобы лимиты и ощущения были как
  на реальном железе, а не «на мощном ПК всё летает».
- **Плюсы**: нет риска кирпича, секундный цикл правок, отладка, демо, проверка Shell на разных API
  (22 / 27) без второго телефона.

Учесть: нативные рантаймы (Python позже) надо будет собирать и под x86; OpenGL ES в эмуляторе
идёт через SwiftShader (медленнее Mali-400); камера — статичная картинка или виртуальная сцена,
а не реальный сенсор.

### Чем писать Shell для ПК

- **ПК-версия — не копия телефонной, а dev-оболочка**: рендер дерева UI, панель `zhal`-крутилок,
  лёгкий `zpkd`. Полный Shell (домой, меню, список задач) живёт на телефоне.
- **Kotlin + Compose Multiplatform (Desktop)** — тот же язык и UI-подход, что на Android, рендер через
  Skia, Windows/macOS/Linux, упаковка в `.msi`/`.exe` через `jpackage`.
- **JavaFX** — легче и стартует быстрее, но UI-код с Android не делится.
- Общее между платформами — **не UI-код, а ядро**: протокол `zdb`, формат дерева UI, контракт `zhal`.
- Compose на K7 (1 ГБ, Mali-400) тяжёлый, поэтому телефонный Shell — на обычных View.

## Привязка к базе и обратимость

Приложения (ZerOS Home, `.zpk`, звонилка, галерея) пишутся под публичные Android API и не зависят
от прошивки. А **SystemUI-мод привязан к версии Android**: он живёт в системном разделе и
обновляется вместе с базой.

- База A5 — LineageOS 17.1 (Android 10, API 29) + TWRP + Magisk; она фиксируется под мод.
  VoLTE не используем: звонки идут через CSFB на 3G/2G, для проекта это не критично.
- Сначала всё делается Magisk-модулями и RRO: их можно отключить и вернуть штатный вид.
- Своя сборка LineageOS нужна, когда требуются правки в коде SystemUI и своя подпись.
- Приложения при этом остаются переносимыми: минимум для них — **API 22**.
- Файлы `.zpk` лежат в приватной папке Home (`filesDir`), общая память — через `MediaStore` и пикер;
  прямой доступ к `/data/media/0` — только с root.

## Принятые решения

1. **Android — ядро и фреймворк.** AMS, WMS, SurfaceFlinger, PackageManager и HAL не переписываем
   и не отключаем. Меняем только то, что видит пользователь.
2. **SystemUI не выключаем — заменяем своим.** Сначала RRO-тема поверх штатного, затем форк
   с нашим поведением (шторка, QS, recents, локскрин, громкость, питание).
3. **ZerOS Home — свой лаунчер** с intent-фильтром HOME; штатный остаётся резервом.
4. **Свои системные приложения** ставятся вместо штатных; штатные не удаляем, а отключаем —
   чтобы был откат.
5. **Root обязателен на A5** (Magisk): замена SystemUI и приложений в `/system`, тихая установка,
   `/data`, оформление. Без root возможна только «лёгкая» версия — Home и `.zpk`.
6. **`.zpk` — параллельный формат, а не замена APK.** `.zpk` не регистрируются в PackageManager/AMS:
   их жизненный цикл ведёт Home/`zhoster`. Android-приложения запускаются штатно через `Intent`.
7. **Права `.zpk` — своя система**, проверяемая и выдаваемая сервисами Home (не через Android-разрешения).
8. **В v0.1 — только web-рантайм.** Python (`zpy`) переносится на более поздний этап.
9. **UI — Android View, не свой GL-рендер.** Экономит ресурсы и даёт бесплатно клавиатуру, IME,
   доступность.
10. **Всё обратимо.** Любой шаг — Magisk-модуль или APK; отключается без перепрошивки.
11. **ПК-версия — dev-оболочка на Kotlin/Compose**, а не копия телефонного UI. Общее ядро:
    протокол `zdb`, формат дерева UI, контракт `zhal`.
12. **Брендинг — часть системы**: свои звуки, шрифт, bootanimation, `ro.build.*` и экран «О телефоне».

## Открытые вопросы

- **SystemUI: RRO или форк?** Начать с RRO-темы (безопасно, не трогает подпись) или сразу форк
  из исходников LineageOS.
- **Подпись.** Для замены `SystemUI.apk` нужен platform-ключ: значит, либо своя сборка LineageOS
  со своими ключами, либо путь только через RRO.
- **Что заменяем первым:** безопасное (часы, калькулятор, файлы, галерея) или сразу звонилку/SMS.
- **Обновления:** Magisk-модуль поверх стока или OTA своей сборки.
- **Где стоит проверка прав `.zpk`:** один раз в `zhoster` при запуске пакета или на каждом вызове API.
- **Как `.zpk` рисует:** `WebView` внутри Home (v0.1) или отдельная Activity/окно на пакет.
